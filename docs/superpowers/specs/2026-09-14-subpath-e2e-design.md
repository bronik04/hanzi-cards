# Сквозные тесты продакшен-конфигурации: приложение под подпутём

## Проблема

Playwright проверяет приложение только при `base: '/'`. В продакшене GitHub Pages
отдаёт его из подкаталога — https://bronik04.github.io/hanzi-cards/, — и `base`
там равен `/hanzi-cards/`. От этой переменной зависят:

- пути ко всем ассетам в собранном `index.html`;
- `start_url` и `scope` в манифесте (`vite-plugin-pwa` выводит их из `base`);
- URL и scope регистрации service worker;
- список URL в прекеше workbox.

То есть вся та часть сборки, из-за которой офлайн уже один раз молча не работал.
Сейчас продакшен-конфигурация не покрыта ни одним автоматическим тестом: сломать
её можно любой правкой `vite.config.ts` или `deploy.yml`, и узнать об этом — только
открыв живой сайт.

## Решение

Второй стенд Playwright, который собирает приложение с `DEPLOY_BASE=/hanzi-cards/`
и гоняет по нему дымовой набор. Обычный прогон `npm run test:e2e` не меняется
ни на строку.

### Разделение стендов

Два стенда разведены по трём осям сразу: свой конфиг, свой порт, свой `outDir`.

```
playwright.config.ts          e2e/           dist/          порт 4173   base /
playwright.subpath.config.ts  e2e-subpath/   dist-subpath/  порт 4174   base /hanzi-cards/
```

Отдельная папка сборки — не про параллельный запуск (в CI это разные машины, а
локально прогоны идут один за другим). Она нужна, потому что `vite preview` читает
файлы с диска на каждый запрос. Если рядом живёт запущенный вручную
`npm run preview`, подпутевая сборка перезаписала бы `dist/` под ним, и он начал бы
молча отдавать HTML с чужим `base`. Это ровно тот класс ошибок «у меня
работает», от которого стенд и должен защищать, так что заводить его с такой
дырой внутри бессмысленно.

`testDir: './e2e-subpath'` лежит вне `e2e/`, поэтому основной конфиг с его
`testDir: './e2e'` новых тестов не видит. Ни `testIgnore`, ни `projects`, ни
вторая запись в `webServer` основному конфигу не нужны — он остаётся нетронутым.

### Конфиг стенда

```ts
webServer: {
  command: `vite build --outDir dist-subpath && vite preview --outDir dist-subpath --port ${PORT}`,
  env: { DEPLOY_BASE: BASE },
  url: `http://localhost:${PORT}${BASE}`,
}
use: { baseURL: `http://localhost:${PORT}${BASE}` }
```

`DEPLOY_BASE` задаётся в `env` самого `webServer`, а не инлайновым присваиванием в
npm-скрипте. Скрипт вида `build:subpath` без переменной собрал бы корневой `base` в
подпутевую папку и врал бы собственному имени; кроме того, инлайновый `VAR=value`
не работает в cmd. Так переменная и подпуть остаются в одном файле с тем, кто их
использует.

Команда вызывает `vite build` напрямую, а не `npm run build`: последний добавляет
`tsc --noEmit`, который в CI уже отработал в джобе `check`.

`BASE` и `PORT` лежат в `e2e-subpath/base.ts` — единственном месте, где записан
подпуть. Его импортируют и конфиг, и тесты, так что ожидания в проверках не могут
разъехаться с тем, что реально собрано. Под `testMatch` по умолчанию этот файл не
подпадает и тестом не считается — так же, как `e2e/fixtures.ts` сегодня.

### Дымовой набор

`e2e-subpath/smoke.spec.ts`, четыре проверки. Хелперы `serviceWorkerActive`,
`serviceWorkerControlling` и фикстура `SHORT_TABLE` импортируются из
`../e2e/fixtures`; дублировать их незачем.

**1. Страница грузится без ответов 4xx.** Копим ответы со статусом ≥ 400 (5xx
ловится заодно и бесплатно), идём на `'./'`, дожидаемся заголовка экрана импорта,
проверяем, что список пуст. Ждать именно отрисованный экран, а не событие load,
обязательно: иначе проверка сойдётся раньше, чем приедут ассеты.

**2. Манифест описывает подпуть.** Снимаем у `link[rel=manifest]` атрибут через
`getAttribute('href')`, а не свойство `.href`: свойство браузер уже разрешил в
абсолютный URL, и разница между корневым и подпутевым `base` в нём видна хуже.
Атрибут в собранном HTML должен быть ровно `/hanzi-cards/manifest.webmanifest` —
это проверка, что `base` доехал до разметки. Затем скачиваем манифест и сверяем
`start_url` и `scope` с `/hanzi-cards/`. Неверный `start_url` означает
установленное приложение, которое открывается не туда, и на глаз это незаметно.

**3. Service worker зарегистрирован со scope подпути.** `registration.scope`
оканчивается на `/hanzi-cards/`, `scriptURL` — на `/hanzi-cards/sw.js`.
Существующий `serviceWorkerControlling` проверяет `toContain('sw.js')`, для этой
задачи слишком слабо: под корневым `base` такая проверка тоже зелёная.

**4. Офлайн работает с первого визита.** Повторяет сценарий
`e2e/offline.spec.ts`, но по `'./'`: дождаться активации и контроля,
`context.setOffline(true)`, `reload()`, убедиться, что экран импорта жив и таблица
парсится. Без промежуточной перезагрузки — по той же причине, что и в исходном
тесте: она замаскировала бы регресс `clientsClaim`.

Записи прекеша и `navigateFallback` у workbox — относительные: он резолвит их
от `self.location`, то есть от пути, куда лёг сам `sw.js`. При смене `base` туда
же переезжает и весь прекеш, поэтому 404 в нём не возникает ни при каком
согласованном `base`, и проверка офлайна (4) остаётся зелёной даже при сломанном
`base`. Падает в этом случае только проверка 3 (scope service worker) — по
другой причине, разобранной там же. Проверка офлайна стережёт не прекеш, а то,
что service worker, зарегистрированный по `/hanzi-cards/sw.js` со scope
`/hanzi-cards/`, действительно перехватывает навигацию и отдаёт приложение из
кеша: это ловит абсолютный `navigateFallback` и абсолютный scope в регистрации.

### Ловушка с goto

При `baseURL` с путём `page.goto('/')` разрешается относительно origin, а не
относительно пути, и уводит в корень домена. Поэтому везде используется `'./'`.

Одного соглашения мало. `vite preview` отвечает на корень редиректом 302 на
подпуть, а GitHub Pages так не делает — там по корню домена лежит чужой сайт.
Значит правка на `goto('/')` прошла бы локально и в CI полностью зелёной, а
сломалась бы только в продакшене. Чтобы это не было делом дисциплины, проверка 1
дополнительно требует `response.request().redirectedFrom() === null`: стенд обязан
отдать приложение прямо по подпутю, без захода через корень.

### CI

Джоба `e2e-subpath` — копия `e2e` с заменой команды на `npm run test:e2e:subpath`
и именем артефакта `playwright-report-subpath` (имена артефактов в пределах одного
запуска обязаны различаться). Отдельная джоба, а не шаг внутри `e2e`: она идёт
параллельно, поэтому общее время CI почти не растёт, и даёт свой красный сигнал —
сразу видно, сломан именно продакшен-`base` или приложение вообще.

`deploy.yml` ждёт заключения всего workflow CI, а не отдельных джоб, так что новая
проверка автоматически становится ещё одним условием публикации. Править
`deploy.yml` не нужно.

## Отвергнутые варианты

**Один конфиг с двумя `projects` и двумя `webServer`.** Всё в одном файле, но
`npm run test:e2e` начал бы поднимать оба стенда и собирать приложение дважды.
Обычный прогон — тот, что разработчик запускает чаще всего; удваивать его ради
экономии на одном файле невыгодно.

**Общий `dist/` на два стенда.** На две строки меньше в игнорах, ценой живой
гонки за содержимое папки с запущенным рядом `preview`. Разбор причин выше.

**Отдельные папки для `playwright-report/` и `test-results/`.** Не делаю: стенды
не бегут одновременно, а перезапись отчёта между прогонами — штатное поведение
Playwright. В CI джобы работают на разных машинах, и различать достаточно имя
артефакта.

**Выводить подпуть из имени репозитория, как это делает `deploy.yml`.** В тестах
`/hanzi-cards/` зашит константой. При переименовании репозитория стенд продолжит
проверять «приложение под каким-то подпутём» — ровно тот класс ошибок, ради
которого он заводится, — и останется валидным, просто подпуть перестанет
совпадать с продакшеном буквально.

## Правки в существующих файлах

Все мелкие, ни одна не трогает поведение обычного прогона.

- `package.json` — скрипт `test:e2e:subpath`.
- `.gitignore` — `dist-subpath/`; строка `dist/` его не покрывает.
- `tsconfig.json` — в `include` дописать `e2e-subpath` и `playwright.subpath.config.ts`:
  список там поимённый, без этого `npm run typecheck` новые файлы не увидит.
- `eslint.config.js` — `dist-subpath` в `ignores`, иначе `eslint .` пойдёт по
  собранным бандлам.
- `.github/workflows/ci.yml` — джоба `e2e-subpath`.

Не меняются: `playwright.config.ts`, `e2e/`, `vite.config.ts`, `deploy.yml`.

## Проверки

`npm run lint`, `npm run typecheck`, `npm run test`, `npm run build`,
`npm run test:e2e`, `npm run test:e2e:subpath`.

Отдельно нужно убедиться, что новый набор действительно ловит то, ради чего
заведён: временно собрать стенд с `base: '/'` и увидеть, что проверки краснеют.
Зелёный набор, который зеленеет и на сломанной конфигурации, бесполезен.

Слияние в `master` — только после код-ревью.
